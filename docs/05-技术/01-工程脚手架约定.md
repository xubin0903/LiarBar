### 3.3 牌堆 JSON 草案

```json
{
  "ranks": ["A", "K", "Q"],
  "wild": "JOKER",
  "claimable": ["A", "K", "Q"],
  "decks": {
    "n3": { "A": 6, "K": 6, "Q": 6, "JOKER": 3 },
    "n4": { "A": 8, "K": 8, "Q": 8, "JOKER": 4 },
    "n5": { "A": 10, "K": 10, "Q": 10, "JOKER": 5 },
    "n6": { "A": 12, "K": 12, "Q": 12, "JOKER": 6 }
  }
}
```

- 工程运行时键为 `n3`..`n6`（ArkTS API 23 不能对 typed 字段下标读 `"3"`）；人数语义仍是 3–6，张数与数值文档一致。  
- `claimable` **不含** `JOKER`（G-Q7）。  
- 5～6 人桌为 P1；MVP 主路径读 `n4`。  
- 重建发牌（GDD §10.1）：对**存活**座位按 `hand_size_default` 从 **完整** `decks.nN`（N=人数）洗牌重发，不是从弃牌堆抽。

### 3.4 判定公式（只实现数值文档，不改语义）

```
is_legal(card, claim)      = card.rank == claim OR card.rank == JOKER
hand_is_clean(cards, claim)= 每张 is_legal
质疑成功                   ⇔ NOT hand_is_clean(上家本手, claim)
```

实现必须放 `engine/`，单测对着这三行；禁止 UI 层重写。

### 3.5 魔法数禁令（验收可勾）

- [ ] `entry/src` 内无 `15`/`8`/`3`/`5` 作为规则常量（枚举下标、数组长度除外）  
- [ ] 超时、命数、手牌、出牌张数、仪式秒数均来自 `Match.config`  
- [ ] SOFT/SLAM/HESITATE 阈值读 `soft_max_velocity` / `slam_min_velocity` / `hesitate_dwell_ms`  
- [ ] 新增键先改数值文档再改 JSON，禁止只改代码

### 4.3 状态后缀（控件与美术共用）

通用交互、命数、出牌方式以后缀换图，主名不变（UI 表 §3）。

| 场景 | 必须用的后缀 | 工程绑定 |
|------|----------------|----------|
| 默认可点 / 按下 / 禁用 | `_idle` `_press` `_disabled` | 所有 `lb_btn_*`；**第一手**质疑 = `lb_btn_challenge` + `_disabled`（文案 `lb_str_challenge_disabled_first`） |
| 手牌 | `_idle` `_press` `_selected` `_empty` | 控件 `lb_cmp_card_{0-4}`；图 `$r` `art_card_*` |
| 仅质疑窗 / 超时 | `_timeout` `_empty` | 手牌 0：`lb_str_hand_empty`；窗结束 `_timeout` |
| **质疑仪式（全岗锁名）** | 见下表四 id，**不是** `_challenge_*` 后缀 | 容器仍 `lb_scr_challenge` / `lb_cover_challenge`；图用 `art_*` |
| 出牌方式 | `_soft` `_slam` `_hesitate` | 对齐 `SOFT`/`SLAM`/`HESITATE`；P1 `_pin`/`_blind` 预留不出芯片 |

质疑仪式 **四拍 id 必须齐全**（负责人锁名）。口播可仍说「起势→揭牌→结果」，工程与用例只认下表：

| 锁名 id | 拍 | 含义 | 绑定 |
|---------|----|------|------|
| `lb_challenge_windup` | 1 起势 | 指控姿态 | `lb_btn_pose_*` · `art_challenge_pose_*` |
| `lb_challenge_standoff` | 2 对峙 | **独立 id**；反应表情 + 押注窗 `lb_cmp_bet_bar` | **禁止**并进 reveal |
| `lb_challenge_reveal` | 3 翻牌 | 逐张翻上家本手 | `lb_cmp_reveal_row` / `lb_cmp_reveal_card_*` · `art_card_glow` |
| `lb_challenge_result` | 定格 | 裁定示意（可叠胜/负变体） | 只示意，**不改判定公式** |

跳过仪式：事件仍是 `SKIP_RITUAL`，切到 `lb_challenge_result`（或直接 `JUDGE`）；**不要**再写 `_challenge_skip` / `_challenge_windup` 这类旧后缀。

## 5. 分支 / 目录约定（与制作人工作流一致）

摘自 [02-制作人工作流与验收](../00-立项/02-制作人工作流与验收.md)，客户端补充如下：

| 前缀 | 用途 | 本岗示例 |
|------|------|----------|
| `feat/design-*` | 策划 / 玩法文档 | 不由客户端开 |
| `feat/art-*` | 美术 | 不由客户端开 |
| `feat/ui-*` | UI 线框与命名 | id 权威在 `feat/ui-wireflow`（PR #3） |
| **`feat/client-*`** | 鸿蒙约定与实现 | **本批：`feat/client-scaffold`**（工程脚手架） |
| `feat/test-*` | 用例/试玩 | 状态机单测日后用 |

| 约定 | 说明 |
|------|------|
| 文档 PR 标题 | `docs:` / `docs(client):` |
| 合入目标 | 日常 PR 只开 **`develop`**；**禁止**开向 `main`（见 CONTRIBUTING） |
| 本批范围 | 交脚手架工程 + 更新本文状态；**不改** GDD/PRD/数值规则正文 |
| 质量门 | 策划 **已会签**（特性服务玩法 + 状态机未发明胜负）；本批改完三拍锁名后请负责人复审 |
| 实现开工后 | 一特性一分支，例如 `feat/client-turn-ui`、`feat/client-privacy-peek` |
| 忽略规则 | 工程文件的忽略写在本地 exclude；密钥不进库（日后若有） |

```
读一页纸 → GDD → 数值 → PRD → 本目录
  → feat/client-* 产出
  → PR（写清对齐哪条决议）
  → 制作人审核 → 合格再给下游实现
```

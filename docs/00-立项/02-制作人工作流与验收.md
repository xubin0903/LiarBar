## 1. 当前阶段边界

- **已完成**：规则与设计文档 v0.2 锁定（见 [审核意见](../审核意见.md)）  
- **文档阶段（当前）**：按岗补齐 `03-鸿蒙与AI` / `04-设计` / `05-技术` / `06-质量` 的本岗 spec（见各目录 README 与建议文件名）  
- **当前不做**：工程业务代码、客户端/服务端实现、可运行 Demo  
- **开工条件**：03～06 本岗 spec 经负责人审核合格后，再进入下游实现  
- **合入**：日常 PR 进 `develop`；`main` 只作发布/演示基线，**仅负责人**在审核通过后合入

## 2. 分支约定

| 前缀 | 用途 | 示例 |
|------|------|------|
| `feat/design-*` | 策划：玩法 / GDD / 数值 / 互动文档 | `feat/design-producer-lock-v02` |
| `feat/art-*` | 美术：风格、皮肤、资源说明 | `feat/art-tavern-skin` |
| `feat/ui-*` | UI：信息架构、界面与交互稿 | `feat/ui-table-ia` |
| `feat/client-*` | 鸿蒙开发：特性 / AI spec、日后客户端 | `feat/client-harmony-spec` |
| `feat/test-*` | 测试：用例、试玩记录、验收清单 | `feat/test-mvp-checklist` |
| `docs/*` | 纯文档：目录、工作流、导航 | `docs/contributing-workflow` |

- **日常基线**：`develop`。功能分支从最新 `develop` 拉出，PR **只开向 `develop`**。  
- **发布/演示基线**：`main`。负责人审核通过后，**由负责人**把 `develop`（或指定提交）合入 `main`。  
- **禁止**直接往 `main` 堆未审内容；**禁止**把日常 PR 开向 `main`。  
- 每天先 `git fetch`，再 rebase 或 merge `develop`（文档阶段也可 `git pull origin develop`）。  
- PR 标题前缀：`docs:` / `design:` / `feat:`。  
- 完整命令与审阅约定见根目录 [CONTRIBUTING.md](../../CONTRIBUTING.md)。

## 3. 标准流程

```
读文档（一页纸 → GDD → 互动 → 数值 → PRD → 本岗目录 README）
  → 从 develop 按岗前缀开分支
  → 按岗产出 03～06 spec 草案（不改已锁规则）
  → 向 develop 提 PR（写清改了什么、对齐哪条 v0.2 决议）
  → LiarBar 负责人审核
       ├─ 不合格 → 返工（同一 PR 或后续 commit）直到合格
       └─ 合格 → 合入 develop → 下游岗可依赖
  → 演示/发布需要时：仅负责人将 develop 合入 main
```

文档阶段先把 03～06 写合格，再开工工程。不要在 spec 未齐时并行堆业务代码。

### 3.1 制作人审核看什么

1. **是否好玩 / 沉浸**：有没有戏、会不会冷场、演示能不能讲清  
2. **是否与 v0.2 决议冲突**：名称、MVP 边界、质疑/手牌耗尽/出牌权等  
3. **是否发明冲突新玩法**：未经拍板不得改胜负规则  
4. **是否删「不做清单」或扩 P0**：默认禁止  
5. **文风**：保持中文、可执行、避免含糊终局  
6. **Git**：PR 是否指向 `develop`；是否误改已锁 GDD/数值/PRD 正文  

### 3.2 合格定义（文档阶段）

- 与 [审核意见 · 已拍板决议](../审核意见.md) 一致  
- 相关章节互相不打架（GDD / 互动 / 数值 / PRD / 本岗 spec）  
- 可交给下游直接当规格用（无「可随机/可再议」摇摆句，除非标明开放调参）  
- 03～06 各自 README 中的「验收标准」能对上

## 4. 岗位依赖（文档阶段）

| 顺序 | 岗 | 输入 | 输出 |
|------|----|------|------|
| 1 | 设计/制作人 | 决议表 | GDD/互动/数值锁定（已完成 v0.2） |
| 2 | 产品 | 锁定 GDD | PRD P0 验收细化（已锁定；扩写另议） |
| 3 | 美术 | 一页纸+互动 | `04-设计/` 风格板、表情符号规范 |
| 4 | UI | PRD 页面草案 + GDD §9 | `04-设计/` 信息架构、界面交互稿 |
| 5 | 鸿蒙开发 | 合格文档 + PRD §8 + GDD §8/§14 | `03-鸿蒙与AI/`、`05-技术/` spec；**合格后再写工程** |
| 6 | 测试 | 规则 + PRD 验收 | `06-质量/` 用例与验收清单；工程开工后补试玩记录 |

## 5. 验收优先级口诀

1. 好玩、沉浸  
2. 规则公平可执行  
3. 演示可讲清  
4. 特性服务玩法（不堆砌）  
5. 工期可交付

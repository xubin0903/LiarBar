## 2. 分支约定

| 前缀 | 用途 | 示例 |
|------|------|------|
| `feat/design-*` | 玩法/GDD/数值/互动文档 | `feat/design-producer-lock-v02` |
| `feat/art-*` | 美术方案、风格、资源说明 | `feat/art-tavern-skin` |
| `feat/client-*` | 客户端相关（实现阶段） | `feat/client-turn-ui` |
| `feat/server-*` | 服务端相关（实现阶段） | `feat/server-rule-engine` |
| `feat/test-*` | 测试用例、试玩记录、验收清单 | `feat/test-mvp-checklist` |

- 基线分支：`main`  
- 禁止直接往 `main` 堆未审内容；一律 PR  
- 文档 PR 标题建议：`docs:` / `design:` 前缀  

---

## 3. 标准流程

```
读文档（一页纸 → GDD → 互动 → 数值 → PRD）
  → 按岗产出草案（同前缀开分支）
  → 提 PR（写清改了什么、对齐哪条决议）
  → 制作人审核
       ├─ 不合格 → 返工（同一 PR 或后续 commit）直到合格
       └─ 合格 → 合并 → 下游岗可依赖
```

### 3.1 制作人审核看什么

1. **是否好玩 / 沉浸**：有没有戏、会不会冷场、演示能不能讲清  
2. **是否与 v0.2 决议冲突**：名称、MVP 边界、质疑/手牌耗尽/出牌权等  
3. **是否发明冲突新玩法**：未经拍板不得改胜负规则  
4. **是否删「不做清单」或扩 P0**：默认禁止  
5. **文风**：保持中文、可执行、避免含糊终局  

### 3.2 合格定义（文档阶段）

- 与 [审核意见 · 已拍板决议](../审核意见.md) 一致  
- 相关章节互相不打架（GDD / 互动 / 数值 / PRD）  
- 可交给下游直接当规格用（无「可随机/可再议」摇摆句，除非标明开放调参）

## 4. 岗位依赖（文档阶段示意）

| 顺序 | 岗 | 输入 | 输出 |
|------|----|------|------|
| 1 | 设计/制作人 | 决议表 | GDD/互动/数值锁定 |
| 2 | 产品 | 锁定 GDD | PRD P0 验收细化 |
| 3 | 美术 | 一页纸+互动 | 风格板、表情符号规范 |
| 4 | 程序（未开工） | 合格文档 | 状态机与实现（日后） |
| 5 | 测试（未开工） | 规则+验收 | 用例与试玩记录（日后） |

---

## 5. 验收优先级口诀

1. 好玩、沉浸  
2. 规则公平可执行  
3. 演示可讲清  
4. 特性服务玩法（不堆砌）  
5. 工期可交付
